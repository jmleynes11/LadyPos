# 26.2.2 Collection Structures

The UPHSD Bookstore Point-of-Sale system uses MongoDB through Mongoose. Its data is organized into collections for accounts, stores, products, customers, orders, receipts, payments, inventory movements, and administrative controls. Orders and completed sales share the transactions collection; purchased items are embedded within each transaction rather than stored in a separate order-items collection.

This section documents 23 collection names resolved from the current application models on 9 November 2026. It describes the implemented schema definitions, not a live database inventory. No database connection or record retrieval was performed. Field constraints and indexes below are schema declarations; installed database indexes and historical record contents were not verified.

## Data representation and relationships

- Each model defines an _id. Most use ObjectId; AccountAdministrationRealm uses a String identifier.
- storeId identifies bookstore scope, while owner retains the resource owner. User.storeIds records store membership. These Mixed fields have custom validators requiring the intended BSON ObjectId values or arrays.
- Transaction.items embeds product references, quantities, unit prices, subtotals, product-name/SKU/category snapshots, and optional clothing sizes. These item subdocuments do not have their own _id.
- Product.sizeStocks stores optional clothing-size quantities; when supplied, they must be valid nonnegative integers totaling Product.stock.
- The bookstore workflow marks monetary records with moneyUnit = PHP-centavos. For these records, 100 centavos equals PHP 1.00. Historical records without this marker require separate unit verification. BookstorePayment and BookstoreSaleReversal store integer monetary amounts validated by their schemas.
- References link users, stores, products, customers, transactions, invoices, and operational records. ObjectId references are application relationships, not database-enforced foreign keys.
- Audit events, stock movements, bookstore operation receipts, bookstore payments, and sale reversals have application middleware that rejects updates or deletion. This is application-level append-only behavior.
- Virtual aliases such as sellingPrice, quantity, products, orderId, and personId are compatibility representations, not additional stored fields or collections.
- A BookstoreOperationReceipt or AccountOperationReceipt stores a command result for replay; it is distinct from a customer invoice or sales receipt.

## Source and scope notes

Collection names and field/index metadata were resolved by importing the model modules locally without calling connectDB or mongoose.connect. The database connection implementation is in [config.js](../backend/config/config.js). Store attribution and currency-marker validation are in [resourceAttribution.js](../backend/models/resourceAttribution.js). Account-role values are defined in [accountRoles.js](../backend/auth/accountRoles.js). Bookstore payment and invoice creation are implemented in [bookstoreOrders.js](../backend/services/bookstoreOrders.js).

The older database-design and database-review documents describe earlier project states. The current source includes Store, stock movements, bookstore payment/reversal records, and account-control models. Financial, Expense, DebtPayment, and InvoiceCounter are included because their model definitions remain in the repository; inclusion does not establish that all are used by the current bookstore interface.
