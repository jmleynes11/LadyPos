# Security and access-control audit

Scope: static first-party source and configuration names, safe synthetic local controller/model tests. No backend startup, live database inspection, external attack, real account creation or credential reproduction. Full evidence and acceptance criteria are in [technical findings](technical-findings.md).

## Control-by-control assessment

**Authentication/passwords:** bcrypt is a dependency and used by login/admin reset/seed, but ordinary provisioning does not hash. Registration issues a token before confirmation. There is no password recovery backend despite a visible inert Forgot Password control. Validate password types/lengths server-side and use a single tested hashing policy. Protect initial admin provisioning. [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) supports salted adaptive hashes; this audit does not introduce a new hashing dependency.

**Session management:** JWT expiry exists; no refresh/session registry, token version or invalidation exists. Client persistence uses localStorage/sessionStorage; stale local values can override session values and logout clears unrelated keys. The guard is UX only. Fix server account checks first; record whether bearer storage is retained or migrated to secure HttpOnly cookies. Cookie migration would require CSRF protections and a CORS/session redesign; none was performed.

**Authorization/data scope:** Most queries include owner; expenses list uses userId; admin user routes are explicitly restricted. These are useful controls, compromised by public admin issuance. Expense admin overrides cross ownership by design, while other admin business queries remain owner-only. No general cross-owner leak is claimed without testing. References populated by ObjectId rely on stored referential integrity; validate owner consistency when writing them. Require current account permissions for price changes, stock adjustment, sale void, financial visibility and account changes under the approved policy.

**Input validation/injection:** Field allowlists exist in several controllers but are inconsistent. IDs and dates may surface cast errors500; quantities use parseInt, amounts coerce/round rather than reject. Raw search strings become MongoDB regex; bound/escape search and validate primitive types. No SQL-query injection surface found because pg is unused. Do not describe MongoDB as injection-proof: schemas and strict request validation remain necessary. No successful injection exploit was attempted.

**XSS:** React text rendering escapes ordinary values. The server log HTML uses innerHTML; replace with textContent or remove viewer. No general rich-text/HTML input feature was found. Browser token storage increases consequences if XSS is possible. CSP/security headers are not configured in Express; proxy policy is unverified.

**CSRF/CORS:** Current application uses explicit bearer Authorization, not cookies. Traditional ambient-cookie CSRF is not the primary demonstrated risk; do not claim a missing CSRF token alone is an exploit. CORS allows localhost5173 and one named Netlify origin, with credentials=true, and permits absent Origin. CORS is not authentication. Public logs precede CORS. Move allowed origins to validated environment configuration, narrow to actual clients and test OPTIONS/error behavior. Reassess CSRF if cookie auth is adopted.

**Abuse/network hardening:** No application login/request rate limiting or security-header middleware found. express.json has its framework default limit; there is no custom business cart/line/page/search limit. Add throttling and bounded validation with measured thresholds; terminate TLS at selected production edge. Proxy/WAF controls are unverified. [Express security recommendations](https://expressjs.com/en/advanced/best-practice-security/) support TLS, input validation and abuse protections.

**Secrets:** Backend environment is tracked, client environment ignored, no examples or secret lifecycle documented. Only variable names were read into the audit. `MONGO_PASS` has no direct use found; MONGO_URI is consumed by connect and seed. All VITE variables are browser build inputs and cannot contain secrets. Do not print connection values, hashes or tokens in audit logs. Rotation and history cleanup require a separate controlled implementation/operations change.

**Dependencies:** initial scans failed ENOTFOUND/ECONNRESET, but later read-only retries succeeded. Backend:8 affected entries, one critical/three high/four moderate. Client:22, twelve high/nine moderate/one low. These counts include inherited and development findings and do not prove application exploitability. The critical backend proxy-addr advisory depends on IP trust behavior; Axios/server and build-tool findings need usage review. See [dependency audit](dependency-audit.md) for package versions and representative advisory sources. Review compatible fixes and regression results; no automatic upgrade/downgrade was applied.

**Uploads/external services:** No application upload endpoints or gateway SDK/webhooks found. Upload hardening is not an active surface. GCash, bank, Grab and Foodpanda strings do not prove verified settlement or integration.

**Database permissions/financial records:** Runtime credential privileges, network access controls, encryption, installed indexes, topology and backups are unknown. Use a scoped application DB user, TLS/private access and separate administrative migration/backup roles. Financial history is mutable/voidable without immutable audit events; expenses are hard-deleted and later payment allocations are incomplete. Introduce durable actor/reason/correlation/time events with redaction and defined retention; console output is not an audit ledger.

## Security release gate

Resolve F01-F03/F05 before handling real accounts or money. Then prove current-account enforcement, capability/owner denial, safe password lifecycle, request validation, payment/invoice idempotency, log redaction and error statuses in an isolated test environment. Review advisory results and the target deployment's actual TLS, DB privileges and backup configuration. No such release approval is implied by this audit.
